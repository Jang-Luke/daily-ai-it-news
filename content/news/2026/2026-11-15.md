# 2026-11-15 AI·IT 개발 뉴스

최근 24시간의 공식 릴리스를 우선하고, 주말의 신규 발표가 적어 중요한 공식 변경은 72시간까지 확장했습니다. 사전판과 공급자 주장은 안정판·독립 검증 결과와 구분했습니다.

## AI Agent·개발 도구

### Next.js canary, 개발 서버에서 관리형 agent instruction 생성

Next.js 16.5.0-canary.50은 `next dev` 실행 때 관리형 agent instruction을 만들고 opt-out을 존중하는 변경을 포함했습니다. coding agent가 project 문맥을 자동으로 얻는 편의가 생기지만, 생성 파일의 내용과 repository 정책·비밀정보 노출 여부를 검토한 뒤 팀 표준에 넣어야 합니다.

- **중요한 이유:** framework가 agent context 생성에 직접 관여하기 시작해 개발 편의와 instruction supply-chain 관리가 함께 필요합니다.
- **발표일:** 2026-11-14 KST
- **원문:** [vercel/next.js v16.5.0-canary.50](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.50)

### GitHub Copilot, 일부 모델 12월 14일 지원 종료 예고

GitHub는 Copilot Chat, inline edit, ask·agent mode와 completion에서 일부 모델을 2026년 12월 14일 종료한다고 예고했습니다. 조직은 모델을 고정한 workflow와 평가 suite가 대체 모델에서도 품질·비용·지연 기준을 충족하는지 미리 확인해야 합니다.

- **중요한 이유:** 모델 종료는 agent 자동화와 승인 모델 정책을 동시에 깨뜨릴 수 있어 migration과 fallback이 필요합니다.
- **발표일:** 2026-11-14 KST
- **원문:** [GitHub Changelog — Copilot model deprecation](https://github.blog/changelog/2026-11-13-upcoming-deprecation-of-selected-github-copilot-models-in-december)

### GitHub Copilot app, Enterprise Server repository 지원

GitHub Copilot app에서 GitHub Enterprise Server 계정을 추가해 remote repository, issue와 pull request를 다룰 수 있게 됐습니다. 사내 코드가 cloud agent context로 전달되는 범위와 app 권한, 감사 log를 조직 정책에 맞게 점검해야 합니다.

- **중요한 이유:** 폐쇄형 repository에도 agent workflow를 연결할 수 있지만 최소 권한과 데이터 경계 검증이 선행돼야 합니다.
- **발표일:** 2026-11-14 KST
- **원문:** [GitHub Changelog — GHES support in Copilot app](https://github.blog/changelog/2026-11-13-github-enterprise-server-support-in-the-github-copilot-app)

### Gemini 4 Hydrogen, GitHub Copilot에서 정식 제공

GitHub는 agentic coding, tool use와 multi-step workflow를 겨냥한 Google Gemini 4 Hydrogen을 Copilot에서 일반 제공한다고 밝혔습니다. 기본 모델 변경 전 repository별 test 통과율, tool-call 안전성, instruction 준수와 token 비용을 기존 모델과 비교해야 합니다.

- **중요한 이유:** 모델 선택지는 늘었지만 production coding agent에는 동일한 benchmark와 human review 기준이 필요합니다.
- **발표일:** 2026-11-14 KST

## 보안·플랫폼

### GitHub AI Scan, REST API로 조직·repository 설정 관리

GitHub code scanning의 AI Scan을 조직과 repository 수준에서 REST API로 켜고 끌 수 있는 public preview가 공개됐습니다. 중앙 policy automation에 연결할 수 있지만 preview API 변경 가능성과 AI 분석의 false positive를 고려해야 합니다.

- **중요한 이유:** 다수 repository의 설정 drift를 줄일 수 있으나 CodeQL·branch protection과 중복 또는 공백이 없는지 확인해야 합니다.
- **발표일:** 2026-11-13 KST
- **원문:** [GitHub Changelog — AI Scan REST API](https://github.blog/changelog/2026-11-13-manage-ai-scan-for-repositories-using-the-rest-api)

### AWS Security Hub CSPM, Organizations 선언형 정책 지원

Security Hub CSPM이 AWS Organizations declarative policy로 account·region별 표준과 control을 중앙 관리하도록 확장됐습니다. 신규 account에 baseline을 자동 적용할 수 있지만 기존 central configuration과의 우선순위와 예외를 migration 전에 정리해야 합니다.

- **중요한 이유:** multi-account 보안 baseline의 누락과 drift를 줄일 수 있습니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — Security Hub CSPM declarative policies](https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-cspm-org-policies/)

### AWS Secrets Manager, account 간 secret 복제 지원

Secrets Manager가 primary secret을 다른 AWS account로 동기화하는 cross-account replication을 지원합니다. replica는 대상 account의 customer-managed KMS key로 암호화되며 rotation도 전파되지만 승격·장애조치 때 application이 읽을 secret을 runbook으로 검증해야 합니다.

- **중요한 이유:** 복구 account에 최신 secret을 격리할 수 있지만 잘못된 권한은 credential blast radius를 넓힙니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — Secrets Manager cross-account replication](https://aws.amazon.com/about-aws/whats-new/2026/11/secrets-manager-cross-account/)

### AWS Batch on EKS, capabilities·seccomp·pod 보안 설정 추가

AWS Batch의 EKS job definition에서 Linux capabilities, seccomp profile, `fsGroup` 같은 pod security context를 설정할 수 있게 됐습니다. restricted profile 아래 필요한 privilege와 syscall만 허용할 수 있지만 실제 workload를 측정해 과도한 capability를 제거해야 합니다.

- **중요한 이유:** batch workload의 최소 권한 적용과 Pod Security Standards 준수가 쉬워집니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — Batch on EKS security context](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-batch-eks-security-context/)

## 데이터베이스·클라우드·아키텍처

### Aurora PostgreSQL express configuration, CloudFormation 지원

Aurora PostgreSQL express configuration을 CloudFormation에서 선언할 수 있게 됐습니다. cluster와 primary instance 생성을 단순화하지만 create-only property의 교체 동작과 production parameter, backup 설정을 명시적으로 확인해야 합니다.

- **중요한 이유:** 빠른 IaC 배포에 유리하되 간소화된 기본값이 운영 database의 가용성·보존 정책을 대신하지는 않습니다.
- **발표일:** 2026-11-14 KST
- **원문:** [AWS — Aurora PostgreSQL express configuration](https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-postgresql-cloudformation/)

### RDS for Oracle, 정기 maintenance 중단 시간 단축

RDS for Oracle은 maintenance 전에 필요한 resource를 최대 30분 앞서 준비해 automatic minor version upgrade와 예약 OS update의 offline 시간을 줄입니다. application connection retry, transaction recovery와 maintenance 관측은 그대로 유지해야 합니다.

- **중요한 이유:** 주문·결제 database patch 부담을 낮출 수 있지만 실제 중단 상한과 회복 동작은 staging에서 확인해야 합니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — RDS for Oracle maintenance](https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-reduces-maintenance-downtime-for-amvu-scheduled-upgrades/)

### Amazon Cognito, OAuth 2.0 token exchange 지원

Cognito가 RFC 8693 token exchange를 지원해 service나 AI agent가 사용자 token을 특정 audience와 좁은 scope의 새 token으로 교환할 수 있게 됐습니다. actor token의 `act` claim으로 중개자를 식별할 수 있으며 refresh token은 발급되지 않습니다.

- **중요한 이유:** MCP server와 backend가 원래 사용자 token을 그대로 전달하는 관행을 줄일 수 있지만 audience·scope 검증이 필수입니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — Cognito OAuth 2.0 token exchange](https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/)

### AWS Systems Manager, Google Cloud VM 자동 onboarding

Systems Manager Cloud Connector가 Google Cloud VM에 SSM Agent를 대규모로 배포하고 AWS·on-premises·Azure 자원과 함께 관리하도록 확장됐습니다. GCP service account 권한, egress와 단일 control-plane 장애 의존성을 점검해야 합니다.

- **중요한 이유:** multi-cloud 운영을 표준화할 수 있으나 한 credential 침해가 여러 cloud로 번지지 않도록 격리해야 합니다.
- **발표일:** 2026-11-13 KST
- **원문:** [AWS — Systems Manager Google Cloud support](https://aws.amazon.com/about-aws/whats-new/2026/11/systems-manager-google-cloud-support/)

## 언어·프레임워크·웹 런타임

### workerd v1.20261114.1, cron 중복 실행·unknown outcome 처리 개선

workerd 최신 릴리스는 시계가 뒤처질 때 같은 cron occurrence를 두 번 실행하지 않도록 하고, retry 중 conditional bucket write가 거절되면 결과를 unknown으로 보고하도록 바꿨습니다. cluster lease, startup snapshot, Rust bridge 경계검사와 WritableStream flush 수정도 포함됐습니다.

- **중요한 이유:** scheduled order 처리와 conditional write는 중복·누락 방지에 직접 연결되므로 upgrade 후 idempotency와 timeout test가 필요합니다.
- **발표일:** 2026-11-14 KST
- **원문:** [cloudflare/workerd v1.20261114.1](https://github.com/cloudflare/workerd/releases/tag/v1.20261114.1)

### Next.js 16.5 canary.50, Turbopack GC·RSC navigation 개선

Next.js 16.5.0-canary.50은 canary에서 minify-before-chunking과 Turbopack GC를 기본 활성화하고 client reference manifest를 줄였습니다. `next start`의 RSC navigation·runtime prefetch, fallback shell 재검증의 반복 prerender와 LCP image 상태도 수정했습니다.

- **중요한 이유:** build size·memory·cache freshness에 영향을 주지만 canary이므로 운영 투입보다 회귀 검증에 적합합니다.
- **발표일:** 2026-11-14 KST
- **원문:** [vercel/next.js v16.5.0-canary.50](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.50)

### Rust 1.100.0, never type·custom allocator 안정화

Rust 1.100.0은 never type과 `extern "custom"`, sample profile 사용을 안정화하고 custom allocator API를 stable로 올렸습니다. `wasm32-wasip3`는 Tier 2로 승격됐고 일부 target 등급과 lint 기본값도 바뀌었습니다.

- **중요한 이유:** allocator와 WASI target의 안정화는 server·embedded·Wasm 생태계에 넓게 영향을 주므로 MSRV와 lint 변화를 확인해야 합니다.
- **발표일:** 2026-11-13 KST
- **원문:** [rust-lang/rust 1.100.0](https://github.com/rust-lang/rust/releases/tag/1.100.0)
