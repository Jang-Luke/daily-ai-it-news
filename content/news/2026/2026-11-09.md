# 2026-11-09 AI·IT 개발 뉴스

최근 24시간의 공개 자료를 우선하고, 주말 동안 공식 발표가 적은 영역은 72시간까지 확장했습니다. 커뮤니티는 이슈 발견에 활용하되 제품·보안·릴리스 사실은 공식 글과 저장소를 우선 확인했습니다.

## AI Agent·개발 도구

### “Claude에서 Pi로” 전환기가 보여 준 agent harness 선택 기준

개발자 Caleb H.가 Claude Code 대신 Pi를 사용하게 된 과정을 공개하고, 단일 제품의 풍부한 기본 기능보다 작은 core와 extension으로 workflow를 직접 구성하는 방식을 선택했다고 설명했습니다. 이는 개인 사용기의 판단이지 보편적 성능 비교는 아니지만, agent 도입에서 model뿐 아니라 context 관리·도구 확장성·update 속도를 따로 평가해야 함을 보여 줍니다.

- **중요한 이유:** 팀 표준을 정할 때 task 성공률과 비용 외에 설정 이식성, provider 교체 가능성, extension 보안 검토 비용을 함께 측정해야 합니다.
- **공개일:** 2026-11-08
- **원문:** [Goodbye Claude, hello Pi](https://caleb.software/posts/claude-to-pi.html)

### GitHub, 코드 생성을 넘어선 agentic engineering 운영 지침 공개

GitHub는 agent가 계획·구현·검증을 순환하는 개발 방식에서 명확한 instruction, 작은 작업 단위, repository context와 자동 검증을 갖추는 방법을 정리했습니다. 공급자의 권고이므로 효과는 각 저장소에서 측정해야 하지만, prompt 한 번으로 큰 변경을 맡기기보다 feedback loop를 설계하라는 핵심은 실무적으로 유효합니다.

- **중요한 이유:** 주문·결제처럼 회귀 비용이 큰 시스템에서는 test, lint, policy check와 사람 승인을 agent loop의 종료 조건으로 명시해야 합니다.
- **발표일:** 2026-11-06
- **원문:** [GitHub Blog — Beyond code generation](https://github.blog/ai-and-ml/github-copilot/beyond-code-generation-a-developers-guide-to-agentic-engineering/)

### agent memory에도 OpenTelemetry 같은 공통 관측 형식이 필요하다는 제안

Lorekit은 agent memory가 제품별 black box가 되지 않도록 memory write/read, provenance, retention과 삭제를 관측할 수 있는 공개 형식을 제안했습니다. 아직 표준이나 합의된 specification은 아니지만, memory 품질을 단순 retrieval 정확도가 아니라 trace와 lifecycle로 평가하려는 문제 제기입니다.

- **중요한 이유:** 개인정보·거래 맥락을 다루는 agent는 무엇을 왜 기억했고 언제 삭제했는지 audit 가능해야 하며, model 교체 시 memory portability도 검토해야 합니다.
- **공개일:** 2026-11-08
- **원문:** [Lorekit — Agent memory needs its OpenTelemetry moment](https://www.lorekit.io/blog/open-agent-memory-format)

### AWS, Claude Code 원격 세션을 AgentCore에서 통제하는 구현 공개

AWS는 Claude Code session을 Amazon Bedrock AgentCore runtime으로 옮기고 identity·network·session control을 적용하는 architecture를 공개했습니다. AWS 예제는 특정 cloud 구성에 대한 안내이며 모든 위협을 자동으로 제거하지 않으므로 IAM scope, egress와 source credential 전달 경로를 별도 검토해야 합니다.

- **중요한 이유:** 원격 coding agent는 개발자 laptop보다 오래 실행되고 더 넓은 자원에 접근하기 쉬워 session isolation, short-lived credential과 audit log가 필수입니다.
- **발표일:** 2026-11-06
- **원문:** [AWS — Extend Claude Code to remote sessions on AgentCore](https://aws.amazon.com/blogs/machine-learning/extend-claude-code-to-remote-sessions-on-amazon-bedrock-agentcore-with-security-controls/)

## 보안·플랫폼

### Claude Code 권한 파일 1,122건에서 비밀정보 노출 정황

Apiiro는 Claude Code의 “다시 묻지 않음” 선택으로 만들어지는 local permission file에 command와 secret이 남고, 공개 GitHub 파일 1,122건에서 이를 발견했다고 보고했습니다. 이는 보안업체의 조사 결과이며 모두 악용됐다는 뜻은 아니지만, agent 설정·transcript가 source code 밖의 새로운 credential 노출면임을 확인시킵니다.

- **중요한 이유:** agent 설정 경로를 secret scanning과 `.gitignore` 기본값에 포함하고, 이미 commit된 key는 history 삭제 여부와 관계없이 즉시 회전해야 합니다.
- **발표일:** 2026-11-07
- **원문:** [Apiiro — Coding agents leaking secrets](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again)

### AWS·Okta, agent의 cross-app 접근 통제 패턴 제시

AWS와 Okta는 Bedrock AgentCore에서 agent가 다른 SaaS를 호출할 때 사용자·agent·application identity와 consent를 나누어 통제하는 두 편의 구현 글을 공개했습니다. vendor reference architecture이므로 실제 적용 시 token audience, revocation, delegated scope와 tenant 경계를 검증해야 합니다.

- **중요한 이유:** “사용자를 대신하는 agent”에 장기 API key를 주는 대신 작업별 위임, 최소 scope와 중앙 audit를 설계할 수 있는 참고안입니다.
- **발표일:** 2026-11-06
- **원문:** [AWS — Govern AI agent access with Okta Cross App Access, Part 1](https://aws.amazon.com/blogs/machine-learning/govern-ai-agent-access-with-okta-cross-app-access-and-amazon-bedrock-agentcore-part-1/)

### Outlook.com, DMARC 없는 발신 도메인 메일 거부 사례 확산

MailRoute는 Outlook.com이 DMARC record가 없는 일부 domain의 메일을 조용히 거부하는 현상을 관찰했다고 보고했습니다. Microsoft의 전체 정책 변경을 공식 확정한 발표는 아니므로 범위를 과장할 수 없지만, 운영자는 실제 bounce·delivery telemetry와 DNS 상태를 즉시 확인할 필요가 있습니다.

- **중요한 이유:** 주문 확인·결제 영수증 메일은 SPF·DKIM alignment와 DMARC policy를 갖추고 provider별 seed test와 bounce alert를 운영해야 합니다.
- **보도일:** 2026-11-08
- **원문:** [MailRoute — Outlook rejecting email without DMARC](https://mailroute.net/blog/outlook-rejecting-email-without-dmarc)

## 웹·클라우드·인프라

### SageMaker Inference, 하나의 endpoint에서 Multi-Instance GPU 지원

AWS는 SageMaker Inference가 여러 instance에 걸친 GPU를 한 model endpoint에서 활용하는 Multi-Instance GPU 구성을 지원한다고 발표했습니다. 대형 model을 단일 instance memory에 맞추기 어려울 때 분산 inference 선택지가 되지만, network overhead와 scaling 단위에 따른 비용은 workload benchmark가 필요합니다.

- **중요한 이유:** throughput만 보지 말고 p95 latency, cold start, 장애 시 shard 복구와 GPU utilization을 함께 측정해야 실제 비용 절감 여부를 판단할 수 있습니다.
- **발표일:** 2026-11-06
- **원문:** [AWS — SageMaker Multi-Instance GPU](https://aws.amazon.com/blogs/machine-learning/sagemaker-inference-now-supports-multi-instance-gpu-to-maximize-gpu-utilization-for-model-endpoints/)

### AWS, ECS Fargate 기반 serverless MCP data-lake 접근 예제 공개

AWS는 Fargate에 MCP server를 배치해 agent가 data lake를 조회하도록 하는 reference implementation을 공개했습니다. MCP interface가 도구 연결을 단순화하더라도 query authorization, tenant isolation과 결과 data의 민감도 통제는 별개입니다.

- **중요한 이유:** agent tool endpoint에는 사용자별 authorization, query allowlist·budget, result redaction과 trace correlation을 넣어야 합니다.
- **발표일:** 2026-11-06
- **원문:** [AWS — Serverless MCP server on ECS Fargate](https://aws.amazon.com/blogs/machine-learning/serverless-mcp-server-for-ai-agent-data-lake-access-on-amazon-ecs-fargate/)

### GitHub, agent-scale 부하를 겨냥한 새 Git storage architecture 설명

GitHub는 repository 증가와 automation·agent가 만드는 대량 동시 작업에 대응하기 위해 storage routing, replication과 장애 격리를 재설계한 architecture를 공개했습니다. GitHub 내부 구현을 그대로 적용할 수는 없지만, agent가 source-control control plane에 주는 부하가 사람 중심 traffic과 다르다는 실측 사례입니다.

- **중요한 이유:** 사내 forge와 CI도 agent별 concurrency·rate limit, merge queue, retry 폭주 방지와 audit provenance를 용량 계획에 포함해야 합니다.
- **발표일:** 2026-11-05
- **원문:** [GitHub Blog — Inside GitHub’s new Git storage architecture](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/)
