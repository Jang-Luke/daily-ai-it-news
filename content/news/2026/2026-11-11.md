# 2026-11-11 AI·IT 개발 뉴스

## AI Agent·개발 도구

### AWS, AgentCore 에이전트 평가 선택 가이드 공개

AWS는 Bedrock AgentCore Evaluations에서 기본 평가기, DeepEval, AutoEval을 작업 완료·주제 이탈·데이터 노출·절차 누락 같은 행위별로 선택하는 playbook을 공개했습니다. 단일 종합 점수보다 실패 유형과 평가 단위를 먼저 정하라는 접근이며, 공급자 도구에 관한 지침이므로 자체 업무의 golden set으로 임계값을 다시 정해야 합니다.

- **중요한 이유:** 운영 에이전트는 정답률 외에도 도구 호출 안전성, 단계 준수와 데이터 경계를 회귀 테스트해야 합니다.
- **발표일:** 2026-11-11 KST
- **원문:** [AWS — The agent evaluation playbook](https://aws.amazon.com/blogs/machine-learning/the-agent-evaluation-playbook-built-in-deepeval-and-autoeval-on-agentcore/)

- **중요한 이유:** 테스트 생성 자동화는 속도보다 요구사항 traceability, fixture 격리와 flaky-test 통제가 먼저입니다.

- **원문:** [AWS — How TCS built an agentic test orchestrator](https://aws.amazon.com/blogs/machine-learning/how-tcs-built-an-agentic-test-orchestrator-with-amazon-bedrock-agentcore/)

### AWS Quick, 반복 업무를 skills와 agents로 구성하는 방식 설명

AWS는 status update, release note, ticket 생성 같은 반복 업무를 Quick의 skill로 encoding하고 agent·조직 데이터와 결합하는 방식을 설명했습니다. 공식 catalog와 custom agent를 함께 쓰는 구조지만, skill이 실행하는 side effect와 데이터 scope는 별도의 정책 계층에서 제한해야 합니다.

### Git, recursive clone·reference·merge 등 6개 취약점 수정

- **중요한 이유:** 개발자 PC뿐 아니라 build runner, source mirror와 ephemeral CI image까지 같은 Git binary inventory로 관리해야 공급망 노출을 줄일 수 있습니다.
- **발표일:** 2026-11-11 KST

## 웹·클라우드·인프라

### AWS, 중앙 ingress를 유지한 self-service regional failover 제시

AWS는 규제 산업의 중앙 ingress proxy를 유지하면서 application team이 ARC Region Switch로 regional failover를 수행하는 reference architecture를 공개했습니다. Transit Gateway peering, Route 53 private hosted zone과 VPC Lattice를 조합하지만, 공급자 예제대로 복구 목표가 자동 보장되는 것은 아니므로 game day가 필요합니다.

- **중요한 이유:** 중앙 보안 통제와 서비스팀의 복구 권한을 분리하면 비상시 cross-team 대기 시간을 줄일 수 있지만 DNS·route convergence와 stale session을 실제로 측정해야 합니다.
- **발표일:** 2026-11-11 KST
- **원문:** [AWS — Self-service regional failover](https://aws.amazon.com/blogs/architecture/self-service-regional-failover-with-amazon-application-recovery-controller-region-switch-and-centralized-ingress-controls/)

### Bedrock 호출 비용·token을 중앙 data lake로 관측하는 패턴

AWS는 여러 계정의 Bedrock invocation log를 한 queryable table로 모아 prompt, token 수, model 선택과 호출별 비용을 분석하는 tokenomics data lake를 공개했습니다. 원문 prompt를 중앙화하면 민감정보가 새로 집중될 수 있으므로 masking, retention과 tenant별 접근제어를 비용 분석보다 먼저 설계해야 합니다.

- **중요한 이유:** agent 비용을 월별 청구액만으로 보면 runaway loop와 비효율 model routing을 찾기 어렵고, 반대로 세밀한 log는 privacy risk를 키웁니다.
- **발표일:** 2026-11-11 KST
- **원문:** [AWS — Amazon Bedrock tokenomics data lake](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-tokenomics-data-lake/)

### workerd 2026-11-10 릴리스, JSRPC 취소·연결 경합 개선

Cloudflare의 `workerd` v1.20261110.1은 pending promise가 폐기될 때 JSRPC 호출을 취소하고, 허용된 연결에서 IPv4를 먼저 시도하며 connection attempt를 race하는 변경 등을 포함했습니다. runtime 내부 변경은 edge application의 timeout·cancellation과 네트워크 fallback 동작에 영향을 줄 수 있어 staging에서 관측해야 합니다.

- **중요한 이유:** request 취소가 downstream 작업·결제 mutation까지 정확히 전파되는지, race가 중복 side effect를 만들지 않는지 확인해야 합니다.
- **발표일:** 2026-11-10
- **원문:** [cloudflare/workerd v1.20261110.1](https://github.com/cloudflare/workerd/releases/tag/v1.20261110.1)

### Next.js canary, prerender status·fetch-cache lock·RSC revalidation 수정

Next.js 16.5.0-canary.46은 prerender가 foreground response status를 바꾸는 문제, origin fetch가 동기적으로 예외를 던질 때 cache lock 해제, static-to-partial revalidation 뒤 배포된 RSC response 문제를 수정했습니다. canary는 production 권장 안정판이 아니므로 관련 증상이 있는 팀도 최소 재현과 회귀 테스트로 선별해야 합니다.

- **중요한 이유:** cache lock 누수와 revalidation 오류는 간헐적 장애로 보이기 쉬워 status·cache hit·RSC response를 함께 trace해야 합니다.
- **발표일:** 2026-11-10 KST
- **원문:** [Next.js v16.5.0-canary.46](https://github.com/vercel/next.js/releases/tag/v16.5.0-canary.46)
